# Done — 2026-08

**Newest entry at the top.** One file per month. This is the dated record of what actually shipped and, more importantly, **what was learned doing it** — the rulings and measured findings that must not be re-derived. `CHANGELOG.md` is the player-facing version of the same events; this file is the engineering version and it is allowed to be long.

An entry earns its place by carrying something the code cannot tell you: why a design was chosen, what was measured, what almost went wrong. "Fixed the thing" is not an entry.

## 2026-08-23 — what the 1.5.0 changelog stopped saying, and why (board b34)

`CHANGELOG.md`'s 1.5.0 entry was rewritten to the house voice adopted from the sibling `LethalGargoyles`
repo (`.claude\skills\changelog-writer`). It went from **2,013 words to 385**, and the cut is the point:
a changelog is a mod-manager release note that a player skims mid-scroll, not a post-mortem. **The
engineering half was not deleted, it was relocated** - most of it already lives in the board rows for
b10, b16, b22 and b23, which are verbatim in `Session_Board_History.md`. Recorded here is what the
rewrite exposed rather than what it moved.

**1. THE ENTRY CONTRADICTED ITSELF, AND THE WRONG HALF WAS THE ONE A READER REACHES LAST.** `### Fixed`
correctly announced that the IL2CPP day-speed no-ops were fixed. `### Notes`, at the bottom, still said
`SetTimeOnCurrentMinute` and `SetTimeSpeedMultiplierDirect` "are currently no-ops in IL2CPP and would
require native IL2CPP field API access to implement properly" - **the pre-b19 belief, written before we
knew Il2CppInterop regenerates native fields as properties.** It had survived b19, b22 and b33. Two
lessons: a `Notes` section is where stale claims go to hide, because nothing routes past it; and **an
unreleased changelog entry accumulates for months and needs re-reading as a whole, not appending to.**

**2. A SECOND STALE BULLET IN THE SAME ENTRY, FOR THE SAME REASON.** `### Added` advertised the
`FindField` helper in `TMAccess`. **b22 deleted `FindField`** when it replaced the reflection with direct
member access. The entry was advertising a feature the shipped DLL does not contain.

**3. THE TEST THAT DOES THE WORK IS LITERAL: could a player notice this without reading the source?**
Roughly forty bullets failed it - `SanitizeHHMM`, `TryInitTimeSync`, `_timeSyncRetrying`, the `Core.cs`
`using` cleanup, `Nullable` set to `annotations`, methods promoted to `public`. None are wrong; none
belong in front of a player deciding whether to hit update.

**4. ONE CUT BULLET IS WORTH KEEPING FINDABLE, because it explains four months of silence.** The build
was compiling against the vendored snapshots in `TNS_Project\Libs\` rather than the game install at
`$(S1Dir)`: the SDK searches `{CandidateAssemblyFiles}` - fed by the default `None` glob over `Libs\` -
**before** `{HintPathFromItem}`, so every reference resolved to a stale local copy and `$(S1Dir)` was
never consulted. **That is why four months of game API changes produced no build error.**
`EnableDefaultNoneItems=false` closes it. It is otherwise recorded only in a board row.

**5. THE HEADING IS THE ONE COPY NOTHING SYNCS, AND IT WAS UNDERSELLING THE RELEASE.** It read
*"Multiplayer Sync & Schedule I 0.4.6f13 Compatibility"* - written before the phone app and silent sleep
existed. Now *"Daily Summary App & Silent Sleep"*. `Version.props` drives the tomls and
`BuildVersion.Value` but not this line; it is hand-edited, so it dates from whenever someone last thought
about it.

## 2026-08-23 — the reference root, and three things that were not obvious (board b8)

`$(S1Dir)` is fixed. The csproj no longer carries a machine path: a gitignored `Directory.Build.props` sets it per configuration, a tracked `Directory.Build.props.example` sits beside it, `-p:S1Dir=` still overrides both, and a `ValidateS1Dir` target fails legibly when something is missing. **Nothing was compiled** — batch 7 held the `BUILD` lock — so this entry is about what was established, not about a green build.

**1. `Directory.Build.props` is imported BEFORE the project, which is the opposite of what "override" suggests.** The instinct is that a props file at the repo root wins over the csproj. It does not: MSBuild imports it first, so the csproj's own `<S1Dir>` assignments were free to overwrite it, and the override would have looked correct while doing nothing. **The fix is on the csproj side** — both definitions now carry `And '$(S1Dir)'==''` and fall through to `$(S1DirMono)` / `$(S1DirIl2cpp)`. **Deleting that condition silently disables every override in the repo**, which is why it is called out in `CLAUDE.md` rather than left as a clever line.

**2. A build could be verified without running one, and that mattered here because the lock was held.** `dotnet msbuild -getProperty:S1Dir` evaluates the project and prints a property without executing targets or touching `bin\`/`obj\`. It confirmed MONO resolving to `...\Schedule I Mono`, IL2CPP to `...\Schedule I IL2CPP`, **and that `-p:S1Dir=C:\some\override` still beats both** — which is the evidence that b7's in-flight audit build was unaffected, rather than a hope that it was. `-t:ValidateS1Dir` runs the new checks alone, same properties, still no output written. **Both are the right tool whenever another session holds `BUILD`, or when the question is "what is misconfigured" rather than "does it compile".**

**3. Reference-resolution failures are WARNINGS, so the real cause never appears in the error list.** A wrong `S1Dir` produces several hundred `CS0246`s — every type in the game's assemblies, missing — and the one line explaining why scrolled past as a warning. That is why this defect survived: the failure was loud but uninformative. `ValidateS1Dir` now fires `BeforeBuild` with six checks that name the cause, and it distinguishes the *flavour* of install too, because pointing the MONO configuration at an IL2CPP copy is a plausible mistake that would otherwise read as the same wall of noise.

**What the checks immediately caught, and the part most likely to be got wrong:** MelonLoader is installed in neither test copy. The MONO arm just needs it present. **The IL2CPP arm needs `MelonLoader\Il2CppAssemblies\*`, which are generated on first launch** — so installing MelonLoader and stopping there leaves that arm exactly as broken, with a folder that does not exist yet. The error text says so outright, because "I installed it" and "it works" are separated by one step nobody remembers.

**And the reason a wrong path is not merely inconvenient:** there are four Schedule I installs on this disk. `...\Schedule I` is the one Mathew plays on, managed by Gale — confirmed independently by Gale having *no* path override for `schedule-i`, so it uses the Steam-registered folder. **The IL2CPP configuration copies its output DLL into `$(S1Dir)\Mods\` after every build.** A plausible-looking `S1Dir` would have quietly deployed development builds into the install he plays on.

## 2026-08-23 — a declared version is a snapshot, not a decision (board b5)

Mathew, on finding `SteamNetworkLib` pinned three minor versions behind: *"Always make sure we are declaring against the latest of our dependencies. I just haven't worked on this mod in awhile, so 1.2.4 was the latest when I was last active."*

**That sentence is the whole finding, and it generalises past this repo.** b4 had treated `MelonLoader = "0.7.1"` as a considered floor and left it alone while fixing the dependency next to it — reasonable-looking, and wrong. **A version number in a manifest records when someone last looked, not what they chose.** On a hobby mod picked up months later, every pin is suspect by default, and the correct reflex is to re-check all of them whenever one is touched, not to fix the one that was asked about.

**Sweeping the rest immediately paid for itself:** `MelonLoader` was at **0.7.1** against a latest of **0.7.3** — a second stale pin nobody had asked about, in the one dependency every single user installs. `Krafs.Publicizer` is **2.3.0** against **2.3.2**, left for a batch that owns the csproj since it is compile-affecting.

**The environment limit worth writing down, because it will be hit again and it looks like a package problem when it is not:** Thunderstore's JSON API answers fine from here (`api/experimental/package/<ns>/<name>/`, `latest.full_name`), but **`thunderstore.io/package/download/...` returns `000` — blocked, not 404.** Two consequences. First, b4 could not establish whether the older 1.2.4 was still downloadable, so "declare what we compile against" was not a verifiable option and 1.5.0 was chosen for being confirmed to exist. Second, **refreshing a vendored `Libs\` DLL can never be done by a session** — it is permanently Mathew's step, and any plan that assumes otherwise is wrong.

**Still split, and it is the part to watch:** declaring 1.5.0 and compiling against 1.2.4 are two different acts, and only the first is done. The DLLs in `Libs\` are unchanged, `Libs\` is gitignored, and **nothing in the repo records what the mod was built against** — which is why this had to be read out of a DLL header. Until item 7 lands, players run 1.5.0 against a mod compiled for 1.2.4.

## 2026-08-23 — SteamNetworkLib was real, and a dependency declared once is a dependency declared three times (board b4)

b1 found that `SteamNetworkLib` was compiled against but shipped and declared nowhere, and filed it as a question rather than a defect because a runtime requirement had not been confirmed. **Mathew confirmed it and supplied the pages.** It is now `ifBars-SteamNetworkLib_Mono` / `ifBars-SteamNetworkLib_Il2Cpp` at 1.5.0 in the tomls, and prose in `README.md`, `Nexus_Description.bbcode`, `MANUAL-INSTALL.txt` and the FOMOD's first page.

**The thing this entry exists for: two storefronts means a dependency is not one edit.** Thunderstore has a machine-readable dependency field, so declaring it there means a manager fetches the library and the player never thinks about it. **Nexus has no equivalent** — its Requirements tab is not read by Vortex — so the same fact has to be repeated as human text in three places, each of which will drift the next time it changes. That asymmetry is now a `CLAUDE.md` hard rule (*anything player-facing exists in more than one copy*), because it applies to every config default and feature line too, not just this library.

**The per-build trap, which is specific to this mod and easy to ship broken.** SteamNetworkLib ships Mono and IL2CPP flavours, exactly like this mod does. A Nexus player picking IL2CPP on the FOMOD's second page and then grabbing Mono SteamNetworkLib has an install that looks complete and does not work. Both build-choice descriptions now name the flavour to take, and the notice page says it outright. On Thunderstore the toml split handles it, which is a good argument for the dependency being declared per-toml rather than in some shared place.

**What was measured, and the one number that could not be.** Both packages are at **1.5.0**, verified live off `thunderstore.io/api/experimental/package/ifBars/...`, and neither carries dependencies of its own. **The vendored DLLs are 1.2.4** (`FileVersion 1.2.4`, `1.2.4+8fae0c6d`), so the mod compiles against 1.2.4 and players will run it against 1.5.0. Declaring 1.2.4 instead would have been the honest option, but **it could not be shown to still resolve**: the experimental endpoint returns only `latest`, and every `package/download/...` probe returned `000` — blocked, not 404, so the absence of an answer is not evidence of absence. 1.5.0 was chosen because it is the version confirmed to exist, and the gap is filed for Mathew (`ToDo.md` item 7) rather than papered over. **`Libs\` is gitignored, so the repo does not record what it was built against** — which is why this had to be read off a DLL header instead of a manifest.

**Left behind deliberately, and parked where it cannot be lost:** the cut 1.4.1 Thunderstore zips still embed the old `manifest.json` with MelonLoader as their only dependency, so **they must be repacked before the next publish or the whole change does nothing for anyone installing them.** That is *Pending manual steps* 3, and it is blocked behind the `S1Dir` defect, since a repack compiles first.

## 2026-08-23 — a Nexus package, and why it is not shaped like the Thunderstore ones (board b3)

`packaging\nexus\` now builds `Packages\TimeNeverStops-<ver>.zip` on every pack, modelled on LethalGargoyles' setup. Built and run (1.4.1, 153 KB, 8 entries, zero backslash entries, fomod validates as XmlScript 5.0); **not uploaded, and never installed by a mod manager** — that is *Pending manual steps* 2 and 3 on the board.

**The design call, which is the part worth keeping.** Thunderstore gets two packages because a package is installed wholesale and the player picks the right build on the website. **Nexus is one page with one download, so the archive carries BOTH builds and the choice becomes a `SelectExactlyOne` FOMOD group.** That is not a workaround for Nexus being different — it is the best thing about the package. **Picking the wrong build is the mistake players of this mod actually make**, and a radio button with "look for GameAssembly.dll" written next to it cannot be got wrong the way "download the correct file from a list" can. The zip root is therefore `IL2CPP\Mods\` and `Mono\Mods\`, one level above the game folder, so a manual installer drags the matching `Mods` folder across — and **there is deliberately no unconditional file in the archive**, because installing both DLLs is the one outcome nobody wants.

**The pack script refuses three things, and the third is specific to this repo.** Two are carried over from LethalGargoyles, where they were paid for in a broken player install: re-running **Vortex's own version-detection regex** over `ModuleConfig.xml`, and validating against the 5.0 schema. **Neither alone is sufficient, and that is the whole lesson** — pointing a validator at the 5.0 schema *bypasses* the version detection, so a FOMOD whose schema string has silently fallen back to XmlScript 1.0 validates clean and then gets rejected by Vortex with a line number that explains nothing. The third guard is new here: **both DLLs must carry `<ModVersion>` as their `FileVersion` or the pack throws.** This repo has stale `bin\` output as a live hazard (see b1), and the Nexus script does not compile — it packages whatever is already there — so without that check a version bump plus a hand-run pack produces a zip labelled 1.5.0 containing 1.4.1.

**It caught its own author on the first run, which is the argument for writing guards before you need them.** The first `ModuleConfig.xml` used a `-----` underline inside an XML comment. A double hyphen is illegal in an XML comment, so the file was not well-formed — the pack failed loudly instead of writing an archive Vortex would have rejected on a player's machine.

**One placement detail that is easy to get backwards:** `pack-nexus.ps1` runs **above** the `tcli`-not-found guard in `build-pack.ps1`. It needs nothing but the two DLLs, so putting it below would mean a machine without `tcli` silently produced no packages at all rather than the one it was perfectly capable of building.

## 2026-08-23 — session docs seeded, and what seeding them turned up (board b1)

Created `Docs\INDEX.md`, `Docs\Session_Board.md`, `Docs\Plans\README.md`, this archive and `ToDo.md`, modelled on the two Lethal Company projects. **Docs only — no code, no build, no pack, no commit.** The structure itself is not worth an entry; the four things found while writing it are, because every one of them is a trap that reads as fine until a session hits it.

**1. The repo looks built, and it is not buildable from clean.** `TNS_Project\bin` holds a DLL for each configuration (IL2CPP 57,344 bytes, MONO 52,224, both dated 2026-04-18), so every surface signal says the build works. But the csproj resolves ~290 references through `$(S1Dir)`, and both values of `S1Dir` live under `D:\SteamLibrary\`, **which is not a path on this machine — not the folder, not the drive-root directory.** The game is installed under `D:\Program Files\Steam App\steamapps\common\` instead, as `Schedule I` (Mono, `Managed\Assembly-CSharp.dll` present) and `Schedule I IL2CPP` (`GameAssembly.dll` present). **The lesson is the shape of the failure, not the path:** stale build output is not evidence that a build works, and on a mod project the reference root is the single most machine-specific thing in the tree. Check `Test-Path` on it before promising a compile-check. Full write-up in *Open defects* 1 on the board.

**2. Repointing `S1Dir` will not be enough for IL2CPP, and finding that out early is worth a lot.** The IL2CPP arm does not reference the game's own assemblies — it references `$(S1Dir)\MelonLoader\Il2CppAssemblies\*`, which MelonLoader generates *after it has been installed and run once* against that install. `D:\...\Schedule I IL2CPP` **has no `MelonLoader\` folder**. So the IL2CPP fix is two steps (install and run MelonLoader, then point at it), and a session that only edits the path will report success on MONO and a wall of missing references on IL2CPP.

**3. `TNS_Project\Libs\` is not what the build compiles against, despite looking exactly like it is.** It holds `Mono\` (a full copy of the managed assembly set) and `MelonLoader\Il2CppAssemblies\`, which is a convincing impression of a vendored reference set. **Only three `Libs\` `HintPath` entries exist in the entire csproj** — `UnityEngine.Il2CppAssetBundleManager.dll`, `SteamNetworkLib-Mono.dll`, `SteamNetworkLib-Il2Cpp.dll`. Everything else goes through `$(S1Dir)`. `Libs\` is also gitignored (`/TNS_Project/Libs/`). **Do not "fix" a missing reference by dropping a DLL into `Libs\`; nothing will pick it up.**

**4. A build here edits tracked files, which makes "just run a build to check" a claimable act.** `build-pack.ps1` rewrites `versionNumber` in both `packaging\*.toml` to match `Version.props` *before* compiling (unless `-StrictVersionMismatch`, which turns the mismatch into a throw instead). The IL2CPP configuration additionally has a `PostBuild` target that copies the output DLL into `$(S1Dir)\Mods\`. Two sessions building at once therefore race on the working tree, not just on `bin`. That is why the board makes `BUILD` a lock and why `-Publish` — `tcli publish` on both packages, irreversible — is called out separately in rule 5.

**Also recorded, not acted on:** `run-build-log.txt` is tracked and stale (its quoted error text cites `run-build.ps1:14`, which no longer matches the script), and `.claude\` is untracked. Both are in `ToDo.md` as decisions for Mathew, not defects.
