# Session Board

**Purpose:** coordination for multiple concurrent Claude sessions on this project. **Mathew does not manage this board — the sessions do.**

**This file is the single canonical rulebook for multi-session work. You (the session) own this file. On your first file read/edit, read this board — it is the live availability map. Add your own claim row BEFORE touching any file, keep its status current, and move it out when the work is done. Never ask Mathew to touch the board.**

**What collides in THIS repo** — it is a small tree, which makes the collisions *worse*, not better, because almost every batch wants the same three files:

* **`TNS_Project\Core.cs` is the whole mod.** It is one file and every feature lives in it, so two sessions editing "different features" are editing the same file and will conflict. `TimeSyncManager.cs` is the only other source file of substance.
* **The build writes tracked files.** `build-pack.ps1` rewrites `versionNumber` in **both** `packaging\*.toml` from `Version.props` before it compiles anything. A build is not a read-only act here.
* **One build command builds BOTH configurations.** `build-pack.ps1` cleans and builds `IL2CPP` *and* `MONO` from the same csproj. Two concurrent runs fight over `TNS_Project\bin` and `TNS_Project\obj` and over the toml writes.
* **BOTH builds now have a `PostBuild` copy into the live game folder** (`$(S1Dir)\Mods\`, gated on `Exists`) — b23 made it unconditional, because IL2CPP-only staging left the MONO test install silently a batch behind. The last build wins on disk regardless of who ran it, and that is now true for both arms.
* **Publishing is one flag away from building.** `run-build.ps1 -Publish` runs `tcli publish` on both packages. See rule 5.

## Protocol (the rules)

1. **Read before you touch.** On your first file operation of the session, read this board. **Only an *Active claims* row with status `authoring` or `building` is a LOCK** — those files belong to another session. A row marked `done`, and anything in **History**, is RELEASED. Everything not in an active `authoring`/`building` row is free.
2. **Claim atomically.** Before editing anything, add a row to *Active claims* and take your batch number by editing the counter below with an EXACT content match: `next = N` becomes `next = N+1`. If that exact-match edit fails, another session bumped it first — re-read the board and retry with the new number. After your claim lands, re-read the board once to confirm your row survived intact; a clobbered write must not go unnoticed.
3. **Claims are terse and canonical.** The *Files* column IS the lock: a bare list of canonical paths (`TNS_Project\Core.cs`, `packaging\thunderstore_mono.toml`, `ToDo.md`) — never prose. A sibling must be able to find a lock by scanning for the real file name at a glance. Scope, caveats and design notes go in *Notes*.
4. **The board is the lock.** If a file you want is in an active claim, work around it. If your task cannot proceed without it, tell Mathew it is blocked and on which session — do not silently edit it. Two active claims may share a file ONLY when both rows name each other explicitly and one session is the designated merge owner — keep that rare and deliberate.
5. **CLAIM THE BUILD, AND NEVER PUBLISH UNASKED.** Take the lock `BUILD` in your *Files* column and set your status to `building` for as long as `run-build.ps1` / `build-pack.ps1` / `dotnet build` runs — it writes `TNS_Project\bin`, `TNS_Project\obj`, **both `packaging\*.toml`**, and (IL2CPP) the game's `Mods\` folder. **`-Publish` is a different act entirely: it uploads to Thunderstore under Mathew's account and cannot be taken back. A session runs it only when he says so, in that session, for that version.** `-SkipPack` is the safe way to compile-check.
6. **Re-check blocked files before you say "waiting."** Locks clear while you work. Right before posting any final message that reports you are blocked on (or deferred work around) a claimed file — and at natural checkpoints in a long session — re-read this board. If the blocking claim is gone or `done`, DO the deferred work now instead of reporting you are still waiting. Reporting "blocked" without a fresh board read is a protocol violation.
7. **Stale claims can be challenged.** Bump your row's *Updated* date every time its contents or status move. Sessions die (closed window, exhausted context): an `authoring` row whose *Updated* is a prior day is suspect — ask Mathew whether that session is still open. Once he confirms it is dead, move the row to History marked `abandoned`; its files are free.
8. **Pick your lane.** Prefer work inside one domain lane (below) to minimise collisions.
9. **Single-writer shared docs.** `ToDo.md`, `CHANGELOG.md`, `README.md`, `CLAUDE.md` and this board collide easily. Claim them like any other file, and always edit with content-anchored matches, never line numbers — they go stale the instant another session writes.
10. **Park work Mathew owes, where it cannot be lost.** Code compiling is NOT the same as working, and **no session can run this game** — every behavioural claim comes back from him or from a MelonLoader log. If your batch needs something only he can do — play a round, host a lobby with a second player, confirm a config value, publish a package — put it in ***Pending manual steps*** below BEFORE your row leaves *Active claims*. A note that only rides a History row gets trimmed and lost. Delete the step the moment it is confirmed done.
11. **Multiplayer claims need TWO machines, and saying so is part of the work.** Time sync runs over Steam lobby data with a host/client split (`TimeSyncManager.cs`, `Core.IsHost`). A solo round proves nothing about client behaviour — the host is the machine that writes the values. Never write "verified" on a sync change off a solo test, and say in the pending step who has to be in the lobby.
12. **Both builds, every time.** `MONO` and `IL2CPP` are one codebase behind `#if` and two different reference sets. A change that compiles in one can fail in the other, and a fix applied to one arm is a bug in the other until it is applied there too. **State in your row which configurations you actually built.**
13. **Move your row out when you are finished.** Flip to `done`, park anything owed under *Pending manual steps*, then move the row to *Recently done* — and when that table passes ten rows, move the oldest into `Docs\Archive\Session_Board_History.md` **verbatim**. Trimming is a MOVE, never a delete: these rows carry findings that exist nowhere else.
14. **Git is real here.** Commit only when Mathew asks. If you do, one batch = one commit, and say the batch number in the message. Never commit `TNS_Project\bin`, `TNS_Project\obj`, `.vs`, `Packages\` or `.claude\worktrees`. **`Packages\` is already ignored** (`**/[Pp]ackages/*` in `.gitignore`), so the built zips are not in the repo — do not "fix" that by adding them.
