## What this mod is

A MelonLoader mod for **Schedule I** that removes the 4:00 AM time freeze, adds a day-speed multiplier, and keeps time synchronised across a multiplayer lobby. Two Thunderstore packages ship from one codebase: `TimeNeverStops_Mono` and `TimeNeverStops_IL2Cpp`.

## Commands

```powershell
.\run-build.ps1 -SkipPack        # compile both configurations, no packaging  <- the safe check
.\run-build.ps1                  # clean + build both + pack all THREE zips into Packages\
.\run-build.ps1 -NoClean         # skip dotnet clean; faster iteration

powershell -File .\packaging\nexus\pack-nexus.ps1              # repack Nexus without rebuilding
```

**Three packages ship from one build.** Thunderstore gets two (`TimeNeverStops_Mono`, `TimeNeverStops_IL2Cpp`) because a player picks the right one on the website; **Nexus is one page with one download, so its archive carries both builds and a FOMOD installer asks which to use.** `packaging\nexus\README.md` owns that layout. **`-Publish` is Thunderstore only — Nexus has no CLI upload path** and is dragged onto the page by hand.

**There are no tests, and there is no way for a session to run this game.** The solution holds one project. Every behavioural claim comes back from Mathew or from a log — `MelonLoader\Latest.log` in the game folder. Turn on `EnableDebugLogging` in the config to get the `TNSLog.Debug` stream, which is where the per-minute state dumps, the sleep-flow trace and the IL2CPP `TimeManager` field dump live. **Compiling is not evidence.** Say what you built and what remains unverified.

Config lives at `UserData\DropDaDeuce-TimeNeverStops\TimeNeverStops.cfg` (created on first run, hot-reloaded within ~1s by a `FileSystemWatcher`).

## Reference sources — READ THESE BEFORE GUESSING AT A GAME TYPE

**`D:\Projects\Schedule 1\References\` holds decompiled game source, and it is shared by every Schedule I project on this disk — it is not part of this repo and must never be copied into it.** As of 2026-08-23 it is a **full decompile of `Assembly-CSharp` and `ScheduleOne.Core` for both arms** (~2,200 files each), so essentially any game type can be looked up without asking. **The path mirrors the namespace exactly:**

```
References\MONO\Assembly-CSharp\ScheduleOne\<Namespace>\<Type>.cs
References\MONO\ScheduleOne.Core\...
References\IL2CPP\Assembly-CSharp\Il2CppScheduleOne\<Namespace>\<Type>.cs
References\IL2CPP\Il2CppScheduleOne.Core\...
```

So `ScheduleOne.UI.DailySummary` is `References\MONO\Assembly-CSharp\ScheduleOne\UI\DailySummary.cs`, and its IL2CPP twin swaps `MONO`→`IL2CPP` and `ScheduleOne`→`Il2CppScheduleOne`. **Read the MONO side for logic** — the IL2CPP files are Il2CppInterop wrappers whose bodies are all `il2cpp_runtime_invoke` stubs, so they prove **names, signatures, visibility and the field→property regeneration**, and nothing about behaviour.

**Use them.** This repo's whole failure mode is guessing at a private game member and shipping a silent no-op. Both entries that used to sit under *Known-broken* were exactly that, and both were fixed the moment the decompile was read. **A claim about a game type that could have been checked here and was not is not a finding.**

Two things already found this way that would cost a session to rediscover:

* **`DailySummary`'s `AddSoldItem` / `AddPlayerMoney` / `AddDealerMoney` / `AddXP` are `[ObserversRpc]` writers that only SEND.** The accumulation is in `RpcLogic___Add*_<hash>`, which runs on every client. Patching the public method tallies **host-only**, and no solo test can catch it.
* **`SleepCanvas.Sleep()` blocks on two unbounded `WaitUntil`s** — see the sleep-flow paragraph under *Architecture*.

## Hard rules

* **ONE SANCTIONED EXCEPTION TO THE RULE BELOW, and it is the only one: `LocalMultiplayer.cs` is MONO ONLY, by Mathew's explicit decision (2026-08-23, b28).** Local same-machine multiplayer exists on the Mono build and not on IL2CPP; IL2CPP multiplayer is Steam-only. **Do not "fix" this by porting it.** The config key `EnableLocalMultiplayer` is created on BOTH arms on purpose — on IL2CPP it warns once at startup if set, so the gap is visible rather than a silent no-op. **And do not record it as impossible on IL2CPP either:** the feature turns on the generic `Multipass.GetTransport<Tugboat>()`, which is the flaky part under Il2CppInterop, but the interop wrapper exposes `_transports` as a plain `public unsafe List<Transport>` that could be iterated instead. That is the same "IL2CPP loses fields" mistake this file already documents once.
* **Every change lands in BOTH arms or it is a bug.** `MONO` and `IL2CPP` are one codebase behind `#if`, and the *entire* abstraction is the `using` alias block at the top of each source file (`ScheduleOne.*` vs `Il2CppScheduleOne.*`). A fix applied to one `#if` branch and not the other compiles fine and ships broken to half the players. Build both before you call anything done.
* **NEVER run `-Publish` unasked.** It is `tcli publish` against Mathew's Thunderstore account, for both packages, and it cannot be taken back. Only in a session where he has said so, for that version.
* **A build edits tracked files, and now stages both arms.** `build-pack.ps1` rewrites `versionNumber` in both `packaging\*.toml` from `Version.props` before compiling, and **both** configurations copy their DLL into `$(S1Dir)\Mods\` in a `PostBuild` target (b23 — it used to be IL2CPP only, which left the MONO test install silently running the previous batch's build). That is why the board makes `BUILD` a lock.
* **Declare against the LATEST published version of every dependency, and re-check rather than carrying the number forward.** Mathew's rule, 2026-08-23: a version already in a manifest is a snapshot of when he was last active on the mod, not a decision. Check at release time and whenever a dependency is touched, and **say what you found even when nothing moved.** Thunderstore answers at `https://thunderstore.io/api/experimental/package/<namespace>/<name>/` (`latest.full_name`); NuGet at `https://api.nuget.org/v3-flatcontainer/<id>/index.json`. **Package downloads are blocked from this environment** — the JSON endpoints work, `thunderstore.io/package/download/...` returns `000` — so refreshing a vendored `Libs\` DLL is always a manual step for him.
* **Anything player-facing exists in more than one copy, and they drift.** The feature list and config keys live in `README.md` (the Thunderstore page body), `packaging\nexus\Nexus_Description.bbcode` (the Nexus page body, **BBCode — Nexus does not render Markdown**) and `packaging\nexus\MANUAL-INSTALL.txt` (shipped in the Nexus zip). Change a default or add a config key and all three want updating in the same batch.
* **`Version.props` `<ModVersion>` is the only version anyone edits.** The tomls are generated from it; `BuildVersion.Value` (the string MelonLoader shows) is generated into `obj\<Config>\VersionInfo.g.cs` from it by an inline MSBuild task. **`CHANGELOG.md`'s heading is the one copy nothing syncs** — bump it by hand.
* **Reflection is the mod's spine, so a game update breaks it silently, not loudly.** The main patch targets `TimeManager.RpcLogic___PassMinute_Client_3316948804` — a FishNet-generated method whose **numeric suffix is a hash that changes when the RPC's signature changes**. If the mod loads clean and simply does nothing after a game update, suspect the patch never attached before you suspect the logic. `TMAccess` and `SCAccess` resolve their targets by string name too. **The suffix is a hash OF THE SIGNATURE, not of the method identity — proven 2026-08-23.** In `DailySummary`, `AddXP(int)` is `RpcLogic___AddXP_`**`3316948804`** — the *same* suffix as `TimeManager.PassMinute_Client(int)` — and `AddPlayerMoney(float)` / `AddDealerMoney(float)` are both `_`**`431000436`**. So identical parameter lists collide by design: **the suffix tells you nothing about which method you got, and a `[HarmonyPatch]` by that string is only unambiguous because the `typeof()` pins the class.** It changes when the *parameters* change, not when the body does. **Checked 2026-08-23 against `References\`: `3316948804` is still the live hash on BOTH arms at 0.4.6f13, and the transcription still matches vanilla** — `_minuteStaggerTime` really is `MinuteDuration / (Time.timeScale * 0.9f)`, and the only divergence is that the mod zeroes `_secondsOnCurrentMinute` before the branch where vanilla does it after, which nothing reads in between. **Re-check both here on the next game update; it is two greps and it is the cheapest insurance in the repo.**

## Architecture

**`TNS_Project\Core.cs` is the mod** — the `MelonMod` entry point, the config system, and every Harmony patch class. `TimeSyncManager.cs` handles multiplayer. `TemplateUtils\AssetBundleUtils.cs` and `Assets\` are unused template leftovers.

**`EnableDefaultCompileItems` is `false`, so a new `.cs` file does NOT compile until it is listed as a `<Compile Include=…>` in the csproj.** It fails as "the name does not exist in the current context", which reads like a namespace problem and is not one.

**The Daily Summary phone app is three files, and the split between them is load-bearing:**

* **`DailySummaryApp.cs`** — the S1API `PhoneApp` subclass. **References S1API and UnityEngine ONLY, never a game type, so it needs no `#if`.** S1API auto-discovers it (a `HomeScreen.Start` postfix constructs every public `PhoneApp` subclass), so it is rebuilt on every scene load and holds no state.
* **`DailySummaryStore.cs`** — the static snapshot, and **the only file in the feature that touches a game type.** Captured by a prefix on `DailySummary.ClearStats`, which fires exactly once per night right before the game wipes the values.
* **`S1APIBridge.cs`** — the firewall. **NOTHING ON AN ALWAYS-LOADED PATH MAY NAME `DailySummaryApp`.** That type derives from `S1API.PhoneApp.PhoneApp`; if S1API is absent the CLR cannot load it, and the only safe outcome is that it is never loaded. `Core.cs` talks to `S1APIBridge`, which probes for S1API **by assembly name through reflection**, and only `DailySummaryApp` itself calls back in. Name the app type from `Core.cs` and a missing S1API becomes a `TypeLoadException` in our startup instead of a missing phone icon.

**The gating fails safe in one direction only.** The vanilla popup is suppressed **only** when the app has actually registered and has not reported a failure. Absent S1API, a failed app, an app that never registered, or the feature switched off all leave the popup working exactly as before. Worst case the player sees the summary twice; they never lose it.

**Config (`Core.OnInitializeMelon`).** MelonPreferences, but redirected: the category is created, then `SetFilePath` points it at the mod's own `UserData` file. `DaySpeedMultiplier` is stored as a **string** parsed with `InvariantCulture` — deliberate, because a float entry serialises by locale and a comma decimal separator would break the file for European users. Every entry has an `OnEntryValueChanged` subscription that sanitises and re-saves, all guarded by the `_updatingPref` flag; **write to a `cfg*` entry without setting that flag and you get a recursive save loop.** `TimeMultiplierOnlyMode` is the master kill switch: when true, every patch early-returns to vanilla behaviour and only the speed loop runs.

**The 4AM bypass (`Patch_Tick_XPMenu.Prefix`).** When the clock would freeze (`CurrentTime == 400`, or inside 400–600 outside the tutorial), the prefix **returns `false` and re-implements the vanilla minute-advance by hand** — day rollover at 2359, hour rollover at `%100 >= 59`, `DailyMinSum`, then the `onMinutePass` / `onUncappedMinutePass` / `onHourPass` / `onDayPass` invocations with the same stagger the original uses. It is a transcription of the original method, so **when the game's `PassMinute` changes, this must be re-read against it, not patched by feel.**

**SILENT SLEEP (b26) IS NOW THE DEFAULT PATH, AND IT INVERTS THE PARAGRAPHS BELOW.** When `EnableSilentSleep` is on *and* the vanilla summary UI is suppressed, `Patch_SleepCanvas_SleepStart.Prefix` **returns `false` and replaces the entire `SleepCanvas` sequence** with `SilentSleepRoutine` — a transcription in the same spirit as the 4AM bypass. It drops the visual and blocking half (black overlay, `SleepingState`, `AddActiveUIElement("Sleeping")`, the timed labels, `StopTransformOverride`, every `WaitForSecondsRealtime`) and keeps every callback:

* **`onSleepFullyFaded` is NOT cosmetic.** `PlayerHealth` subscribes to it with `SetHealth(100f)` — skip it and sleeping stops healing.
* **`SetHostSleepDone(true)` is the only thing in the entire game that releases `TimeManager.WaitForSleepEnd`**, and therefore the only route to `onSleepEnd` **and** to `SaveManager.Save()`. `onSleepEnd` is where employees are marked unpaid for the new day, `DailySummary.ClearStats` runs (our capture hook), cartel deals expire, the mix operation is re-driven and three quests check their start conditions. **Bypassing `SleepCanvas` without calling this silently freezes the entire day rollover.**
* **`onSleepEndFade` is story logic, not a fade.** `Quest_SinkOrSwim.CheckArrival` spawns the loan-shark vehicle and completes its entry; `Quest_TheDeepEnd.SleepFadeOut` teleports the player to the Thomas meeting.
* Both are `UnityEvent`s and therefore also prefab-wired. **Invoke them; never reimplement their known subscribers** — a decompile cannot show you the inspector.

**The gate has a third clause that looks wrong until you check it: silent sleep engages only when `DailySummaryPatch.ShouldSuppressSummaryUI()` is true.** `DailySummary.Start()` does `State.InitializeDefaultParent(SleepCanvas.SleepingState)`, so the vanilla popup pushes onto a state machine silent sleep never puts on the stack. No S1API, or a failed app, therefore falls back to the vanilla sleep screen *with* its popup. The player is never left with no summary.

**`Patch_SleepCanvas_AddPostSleepEvent` exists because vanilla drains that queue inside the coroutine we no longer run.** Without it the list grows one `RankUpCanvas` entry per night forever. Both post-sleep `StartEvent` bodies were read in full and are pure presentation, so dropping them costs nothing — their content is captured into the phone app instead.

**When silent sleep is engaged, `TryRunSleepEndCleanup` deliberately does nothing.** `EnsureHUDReset` re-locks the mouse, re-enables the inventory, forces `CanMove` and unloads the `"Back"` input module — correct after vanilla's sleep screen held the player captive, and a random yank on someone who has been walking around uninterrupted. The decision is **latched** at `SleepStart` (`SilentSleepEngaged`) rather than re-read, because the config hot-reloads within a second and the app can report a failure mid-night.

**Everything below describes the `EnableSilentSleep=false` path, which is still live and still the fallback.**

**The sleep and daily-summary flow is the fragile part, and it is spread across six patch classes plus a watcher.** `SleepStateWatcher` (a per-frame coroutine) edge-detects `TimeManager.IsSleepInProgress`; `Debug_TimeManager` postfixes the `StartSleep` / `EndSleep` / `SetHostSleepDone` RPCs; `Patch_SleepCanvas_SleepStart` defers sleep until the local UI stack is empty (with a cutoff time and a 30s realtime timeout); `Patch_Tick_XPMenu.Postfix` triggers `StartSleep` for the awake-summary feature and force-closes stuck post-sleep canvases. **Three independent paths can reach sleep-end cleanup in quick succession**, which is why it funnels through `TryRunSleepEndCleanup` behind the `_sleepEndCleanupDone` one-shot. Several guards exist purely to unstick the engine (`suppressForSleep` cleared when not sleeping; `IsSleepInProgress` forced false when `HostSleepDone` is set) — **those are load-bearing workarounds for real hangs, not dead defensive code.**

**And now we know exactly what the hang IS. Read `References\...SleepCanvas.cs` before touching any of it.** `SleepCanvas.SleepStart` runs one long `Sleep()` coroutine that blocks on other objects twice, and **both blocks are unbounded `WaitUntil`s with no timeout of their own**:

1. `DailySummary.Open()` then `yield return new WaitUntil(() => !DailySummary.Instance.IsOpen)`. Safe as the mod stands, because the `Open` prefix returns `false` before `IsOpen` is ever set, so the wait passes instantly — **but anything that lets `Open()` run without a matching `Close()` deadlocks the night.**
2. For each queued `IPostSleepEvent`, in `Order`: `pse.StartEvent(); yield return new WaitUntil(() => !pse.IsRunning);`. **`RankUpCanvas.StartEvent` and `RegionUnlockedCanvas.StartEvent` set `IsRunning = true`, and NOTHING IN ANY DECOMPILED SOURCE EVER SETS IT BACK — only `EndEvent()` does, and `EndEvent` has no code callers at all.** It is wired to an animation event or a button in the prefab. So if that animation never plays or the canvas is disabled, the sleep coroutine waits **forever**. **That is why `ClosePostSleepCanvases` calls `EndEvent()` explicitly — it is the release valve for a guaranteed deadlock, not tidy-up.** Both canvases use `UIScreenManager.AddScreen`/`RemoveScreen`, never `AddActiveUIElement`, so force-closing them cannot leak an active UI element.

**The post-`SetHostSleepDone` tail is 1.1s normally and 6.1s+ when a sleep message is queued** — `1f` for `TimeLabel`, then optionally `0.5 + 0.5 fade + QueuedMessageDisplayTime (default 3f) + 0.5 fade + 0.5` for `QueuedSleepMessage`, then `0.1f`, then `RemoveActiveUIElement("Sleeping")`. The 1.1s figure is what b16 measured as 1.14s. **`QueueSleepMessage(string, float displayTime = 3f)` is public and the game uses it, so the tail is not a constant — see `ToDo.md` item 16.** Note also that `"Sleeping"` is removed **third-from-last**, not last: `SleepingState.PopFromDefaultParent()` and a 0.5s `LerpBlackOverlay(0f, 0.5f)` still follow it, so the screen is black for another half second after that signal.

**`TMAccess` / `SCAccess` — the reflection layer, and the biggest parity trap in the repo.** They write `TimeManager` state the game keeps private. The MONO arm builds real delegates from property setters and reaches `_secondsOnCurrentMinute` and `<TimeSpeedMultiplier>k__BackingField` as fields. **The IL2CPP arm's `FindField` lookups resolve to null, so `SetTimeOnCurrentMinute` and `SetTimeSpeedMultiplierDirect` are silently no-ops there** (the code says so at the call site and warns once at static init).

**But the reason is NOT that the data is unreachable, and reading it as "IL2CPP loses fields" forecloses designs that work.** Verified 2026-08-23 against the decompile in `References\` (see *Reference sources* below): **Il2CppInterop regenerates every native instance field as a `public unsafe` PROPERTY on the interop wrapper — getter AND setter — reading and writing the native offset directly.** `AccessTools.Field()` / `Type.GetField()` therefore find nothing, which is the whole of the bug; direct member access works fine. Two naming rules, and the second is what actually bites:

* **Ordinary fields keep their name.** `_secondsOnCurrentMinute` is `public unsafe float _secondsOnCurrentMinute { get; set; }` on IL2CPP.
* **Auto-property backing fields are RENAMED:** `<Name>k__BackingField` becomes **`_Name_k__BackingField`**. So `<TimeSpeedMultiplier>k__BackingField` is reachable on IL2CPP as `_TimeSpeedMultiplier_k__BackingField`. The whole `TimeManager` set exists this way — `_CurrentTime_k__BackingField`, `_ElapsedDays_k__BackingField`, `_DailyMinSum_k__BackingField`, `_IsSleepInProgress_k__BackingField`, `_HostSleepDone_k__BackingField`.

**So both documented no-ops are fixable** — `#if IL2CPP` direct member access, or `AccessTools.PropertyGetter`/`PropertySetter` reflectively. Neither fix is applied yet: see `ToDo.md`. **The rule that still holds, and the only one worth memorising: never reach for a FIELD by reflection if it has to work on IL2CPP.** Property setters work on both arms because they are methods.

**Multiplayer (`TimeSyncManager.cs`).** Time is broadcast as **Steam lobby data** through `SteamNetworkLib` — four `__tns_*` keys (time, elapsed days, timestamp, multiplier). The host writes on hour change, clients read on a 10s loop plus a `LobbyDataChanged` event, and only correct when off by more than the threshold. A client stores its original multiplier and restores it on leaving. Init is deliberately patient — a burst of three attempts on the `Main` scene, then an indefinite 15s poll — because Steamworks is not up when the save loads, and a friend can join a solo session an hour in. **`Menu` scene load resets all of it.**

* **There are TWO different meanings of "host" in this codebase and they are not interchangeable.** `Core.IsHost` is `Player.Local.IsHost` (the game's answer, used to decide who enforces the multiplier onto `TimeManager`). `TimeSyncManager.IsHost` is `_steamClient.IsHost` (the Steam lobby owner, used to decide who writes lobby data). They agree in practice; read the right one for what you are asking.
* **Client-side multiplier sync goes through `TMAccess.SetTimeSpeedMultiplierDirect`, because `SetTimeSpeedMultiplier` has a server-only guard** — which means, per the point above, **that path is a no-op on IL2CPP today, and it is fixable** (`_TimeSpeedMultiplier_k__BackingField`, or the `TimeSpeedMultiplier` property setter, which the decompile shows exists on both arms — private on MONO, exposed by the interop wrapper on IL2CPP).
